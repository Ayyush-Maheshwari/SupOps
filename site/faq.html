FAQ

Straight answers.

What SupOps can and cannot do, what it needs, and what is not built yet.

Safety and control

Can it run commands on prod without me?

Only read-only and low-risk commands run on their own, such as df, systemctl status and kubectl get pods. Medium and high-risk actions pause and wait for a person, showing the exact command, the stated intent and why it was flagged. Forbidden actions, like rm -rf /, can never run, no matter who approves. Autonomy is configurable per project and agent, and a production target always raises the bar.

What if the model hallucinates or gets prompt-injected through a log line?

Shell commands are parsed, not pattern-matched, and anything that cannot be read statically (command substitution, backticks, a variable that could become a command name) fails closed at high. The risk engine has five stages, and each may only raise the tier, never lower it. A log line saying "pre-approved by ops" therefore buys an attacker more approval prompts, not fewer.

Can a command run twice or get lost across a restart?

A run paused at an approval gate resumes identically hours or deploys later, because the conversation is rebuilt from the database. A command that was dispatched but never confirmed is marked unknown_outcome and is never silently re-run.

Can I require a second person to approve?

Yes. Approvals support roles and a second-approver option, and the Approvals page keeps a record of who approved what.

What if it cannot find the root cause?

Inconclusive is an allowed answer. Diagnoses must cite the evidence they were given, and a citation to evidence that does not exist is flagged. Checks whose metrics you do not collect are listed as not measured rather than guessed.

Setup and access

Does it install anything on my servers?

No. SupOps plugs into Prometheus, Grafana, Alertmanager, Loki, Elasticsearch, Kubernetes and Slack through their APIs, and acts over SSH or kubectl using credentials you give it. Nothing is installed on your machines.

What permissions does it need?

Read access to your observability tools is enough for evidence, diagnosis and forecasts. To make changes it needs an SSH user or a Kubernetes service account, and you choose how much power that has: the cluster setup script offers read-only view or edit, and you can restrict which namespaces agents may touch. Advisory mode needs no access at all.

What do I need to run it?

Docker with Compose is enough: docker compose up --build runs the API, live stream, web UI and database in one container. For development you need Node.js 22 or newer. You also need a model endpoint, and a free Gemini key works. A vision-capable model is needed to read screenshots and diagram images.

Can it work if I cannot give it SSH or credentials?

Yes. Advisory mode cannot log in to or change anything. It works from your description, screenshots and approved runbooks, ranks likely causes, and gives you read-only checks, the fix, how to verify it and how to roll it back. Each suggested command is rated by the same risk engine. By default it can also make read-only network checks from the SupOps server, which you can switch off.

How do I deploy it securely?

Run it on a private network or behind a VPN, and do not expose it to the internet as is. It serves plain HTTP by default, which works but means browsers will not offer some features such as installing the app or the microphone off localhost. Give each target the least privilege that works, keep production targets marked as prod, and back up the supops-data volume, which holds the encrypted credentials and the master key.

Models and data

Which models can I use, and where does my data go?

SupOps speaks the OpenAI-compatible chat completions protocol, so Gemini, Ollama, LM Studio, vLLM, LiteLLM, OpenRouter or any compatible endpoint works by changing a base URL and model name in Settings. What is sent to the model is what a run needs: your question, command output and the runbooks it is given. Use a local model if that must not leave your network. Your API key is encrypted at rest and never sent back to the browser.

Are my credentials safe?

SSH and cluster credentials are encrypted at rest with AES-256-GCM. Passwords, keys and tokens found in imported documents are replaced with [REDACTED], and anything that would print a live credential pauses for a human instead of running as a free read.

Is there an audit trail?

Yes. Every run keeps its commands, outputs, risk rating and outcome, and can be exported as a PDF or Markdown report. Approvals record who decided and when. Closed alerts, incidents and metric samples are kept for 15 days by default, which you can change, and open ones are never removed.

The project

How does it relate to Datadog, PagerDuty or my existing monitoring?

It is not a monitoring or paging system and does not replace one. It sits on top of the Prometheus, Grafana and Alertmanager you already run, reads their alerts, and works out why and what to do. It is self-hosted, open source and works with any model.

What is not built yet?

On the roadmap: cloud accounts (AWS, GCP, Azure) through a sandboxed toolbox, GitHub/GitLab and CI/CD integration, multi-step scripts with per-line risk checks, and rules learned from past denials. None of those are available today.

Is it production-ready?

We make no production-readiness claim and publish no benchmark numbers. The risk engine is covered by a corpus, parity and fuzz test suite you can read, and the sensible way to adopt it is gradually: start in Advisory mode, then give it a read-only user, then allow approved changes on staging before production.

How do I report a bug or a security issue?

Open a GitHub issue for bugs and ideas. For anything security-related, report it privately through the repository Security tab, as described in SECURITY.md, rather than in a public issue.
